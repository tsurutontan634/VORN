# まちねこ事務局AI（仮称）— VORN Challenge 2026 プロトタイプ

**地域猫の世話をする人が、受付も報告も更新も落とさずに回せて、担い手が代わっても市に情報が残る。**

地域猫活動の担い手（無償・少数・高齢）に、制度（自治体・基金・病院）が押し付けている時間軸と引継ぎの摩擦を消す。
コロニーを1つ登録すると、その自治体の要綱を LLM が読んで、受付日・必要書類・報告期限・更新期限を逆算した日程を持ち、期限が来れば促し、様式を埋めて出す。市の側には登録コロニーの状態と期限が一覧で残る。
市民面（ボランティア）と自治体面（医療衛生センター職員）の二面構成。課題定義は `HANDOFF.md` §2。

背景・一次情報・戦略は `HANDOFF.md`、作業ルールは `CLAUDE.md`。

## 誰が、何に使うか

- **市民面を使う人**：京都市内で地域猫の世話をしている個人ボランティア。町内会等への説明と同意は済んでいる前提。会話で状況を聞き取り → 要綱に照らして不足を指摘 → 第1号様式・第6号様式を埋めた DOCX を出力して提出 → 周知チラシ → 日程表 → 1年後の年次報告も会話で提出。
- **自治体面を使う人**：京都市医療衛生センターの職員。登録コロニー一覧（区・頭数・耳カット済・登録日・次回報告期限・更新期限・状態）と、コロニー詳細（提出された申請書・計画書・報告がそのまま見える）。書類審査後に「登録する」を押す。
- **やらないこと**：捕獲の手順、町内会への説得、里親探し、子猫の育て方。聞かれたら範囲外と断る。

## なぜ AI か（設計の核）

自治体ごとに要綱が違い、それが自然言語（PDF/DOCX）で公開されている。
このツールは **要綱をコードに書かない**。`municipality/<自治体>/sources/` に置いた一次資料を LLM がそのまま読み、規則・様式の項目・工程・期限を毎回抽出する。
自治体を替えるときはフォルダを差し替えるだけ（実装は京都市のみ）。

## 画面の流れ（左メニューの 1→7）

市民面のどの画面でも先頭に「次にやること」が出る。要綱から抽出した工程と台帳の状態から、次の提出物と期限を組み立てる（`machineko/next_actions.py`。様式名や日数はコードに書かない）。

| 工程 | 何をするか | LLM の役割 | コードの役割 |
|---|---|---|---|
| 1. 聞き取り | チャットでコロニー情報を集める | 質問を出し、回答を構造化データに変換 | データの保持・表示 |
| 2. 要綱照合 | 規則を抽出し、不足・注意・OK を出す | 一次資料から規則抽出（根拠の引用付き）→ 照合 | 表示 |
| 3. 書類出力 | 第1号様式・第6号様式を埋めて提出。登録後は第4号様式（手術実施申請書） | 様式 DOCX のセル構造と記載例を読み、「どのセルに何を書くか」を決める | 指示どおりにセルを書き換えて DOCX 出力、台帳へ「申請中」で登録 |
| 4. 周知チラシ | 「地域へのお知らせ」本文 | 参考様式に沿って本文生成 | 表示・ダウンロード |
| 5. 日程表 | 申請→審査→登録→周知→捕獲→持込→リターン→年次報告→更新 | 工程・誰が日程を決めるか・期限の根拠を抽出 | **日付計算**（LLM に計算させない） |
| 6. 自治体面 | 登録コロニー一覧と詳細。職員が「登録する」 | — | 状態を日付と報告履歴から計算（申請中／登録済／報告待ち／報告済／期限超過） |
| 7. 年次報告 | 会話で活動状況を報告して提出 | 質問を出し、第5号様式の項目に変換 | 台帳に追記、第5号様式 DOCX を出力。自治体面の状態が「報告済」に変わる |

スクリーンショットは `docs/screenshots/`。

## 動かし方

```bash
pip install -r requirements.txt
export ANTHROPIC_API_KEY=sk-ant-...   # 無ければモック応答で動く
streamlit run app.py
```

- APIキーが無いときは **モック応答** に自動で切り替わる（サイドバーに表示）。モックは UI を最後まで通すための固定台本で、`machineko/mock.py` にある。本番経路では使わない。
- モデルは環境変数 `MACHINEKO_MODEL` で変更可（既定 `claude-sonnet-5`）。
- `MACHINEKO_MOCK=1` でキーがあってもモックを強制。
- 「すべてリセット」で台帳もデモ初期状態（ダミー4件）に戻る。
- テスト：`python -m pytest -q`

## 2自治体目：高島市（基金型）

`municipality/takashima/` はどうぶつ基金「さくらねこ無料不妊手術事業（行政枠）」に参加する高島市のプロファイル。市HP本文・基金FAQ・基金規約の3本を `sources/` に置いてある（交付要綱PDFと様式は未取得。様式は .doc と PDF のみの配布で DOCX が無いため、報告書などは資料の項目に沿って生成）。
京都市と同じアプリで、サイドバーの自治体を切り替えるだけで次が変わる。規則はコードに書いていない。

- 要綱照合：「毎月6日〜末日に申請、翌々月分」「報告しないと次の申請不可」「写真4種類」などが根拠付きで出る
- 日程表：受付期間から「準備完了日→最短の申請日→チケット有効期間→この受付を逃すと+◯日」を計算する（`schedule.earliest_schedule`。京都市は受付期間の定めが無いので「規則上の待ちなし」と出る）
- 自治体面：チケット型の状態（申請中／交付済／報告待ち／報告済／期限超過）。台帳は自治体ごとに別ファイル

## 一次資料の配置（重要）

`municipality/kyoto/sources/` に京都市の配布ファイル（要綱PDF、第1号・第6号様式DOCX、記載例PDF、お知らせ参考様式PDF）を置いてあり、起動時に自動で読み込む。
一覧は `municipality/kyoto/profile.yaml` と `sources/README.md`。`tirasi.pdf`（リーフレット）は画像のみでテキストが取れないため LLM には渡していない。
第1号・第6号様式は配布 DOCX の表セルに直接転記する。第5号様式（活動状況報告書）は配布 DOCX が無いので要綱の様式に沿って生成する。

## 構成

```
app.py                      Streamlit UI（1画面、左メニューで工程を切替）
machineko/
  profile.py                自治体プロファイルと一次資料の読み込み（PDF/DOCX/MD → テキスト）
  colony.py                 コロニー情報のデータ構造と JSON Schema
  llm.py                    Anthropic API ラッパー（構造化出力・prompt caching・モック切替）
  intake.py                 1. 聞き取り
  rules.py                  2. 要綱照合（規則抽出 → 照合）
  documents.py              3. 書類出力（項目生成 → DOCX）
  flyer.py                  4. 周知チラシ
  schedule.py               5. 日程表（日付計算はここ）
  next_actions.py           「次にやること」カード（工程・台帳状態から組み立て）
  registry.py               台帳（自治体面のデータ。JSON 永続化、状態計算）
  report.py                 7. 年次報告
  mock.py                   APIキー無しで動かすための固定応答（京都市）
  mock_takashima.py         同（高島市）
municipality/kyoto/
  profile.yaml              自治体の基本情報と資料一覧（規則は書かない）
  sources/                  一次資料の置き場
municipality/takashima/     2自治体目（基金型）。構成は同じ
demo/sample_colony.json     デモ用コロニー（左京区・11頭・活動者3名）
demo/registry_seed_kyoto.json      自治体面のダミー4件（期限超過・報告待ち・更新待ち・申請中が1件ずつ出る）
demo/registry_seed_takashima.json  同、高島市3件（期限超過・報告待ち・申請中）
data/registry_<id>.json            実行時の台帳（gitignore。初回起動時に種データから作られる。「すべてリセット」で戻る）
tests/                      日付計算とモック経路の一気通貫テスト
```
